### 使用Redis解决了在集群模式下的Session共享问题，使用拦截器实现了用户的登录校验和权限刷新

### **为什么用 Redis 替代 Session？**

原生的 Session 通常保存在单台服务器的内存中。在微服务架构或集群部署的后端应用（多实例部署）中，多台服务器并不共享内存状态。当用户的请求被负载均衡切换到另一个节点时，就会出现登录状态丢失（Session不一致）的问题。

**解决方法：** 使用 Redis 这个独立的分布式缓存中间件来存储会话。用户登录后，服务端生成随机 Token 作为 Key，将用户信息存入 Redis 并把 Token 下发给客户端。所有应用节点都通过同一个 Redis 校验登录态，从而避免进程内 Session 不共享。

### **还有其他解决方法吗？**

有，最主流的替代方案是采用 **基于 JWT (JSON Web Token) 的无状态认证机制**。
服务端不再保存任何状态（不查 Redis，不存 Session），而是将用户的身份信息（User ID、权限等）和过期时间进行签名并打包成一个 JWT 下发给客户端。每次请求客户端在 HTTP 请求头中携带 JWT，服务端只需校验签名的合法性和时效性即可鉴权。

*对比：* JWT 减少 Redis 查询，但服务端较难让单个 Token 立即失效；Redis + Token 可以通过删除当前 token key 实现退出或主动失效，代价是每次鉴权依赖 Redis。

### **说说你的登录流程？**

<img width="1802" height="847" alt="image" src="https://github.com/user-attachments/assets/4d04f2c4-7932-49dd-8ae4-73542587ea59" />

当前代码只实现手机号验证码登录；`SendCode` 在 debug 模式把验证码写入日志，短信网关尚未接入。验证码校验通过后：

1. 服务端生成一个随机且唯一的字符串作为 Token。
2. 将用户的核心脱敏信息转为 `UserDTO` 对应字段，以 Hash 存入 Redis，Key 为统一前缀加 Token，并设置 30 分钟滑动过期。
3. 服务端将该 Token 返回给前端（通常由前端存在 localStorage 中）。
4. 客户端随后的每次请求，都会将此 Token 附加在 HTTP 的 `Authorization` Header 中带给服务端。

### **怎么使用 Gin 的中间件（拦截器）实现这些功能？**

系统中设计了两层优雅的 Middleware 中间件结构：
<img width="1839" height="898" alt="image" src="https://github.com/user-attachments/assets/de16cfb6-48f3-4c28-8427-4df1561e430c" />

1. **第一层（全局中间件 `RefreshTokenInterceptor`）：**
   注册在全局路由上。它负责拦截所有请求，尝试从请求头提取 Token。如果提取到了，就去 Redis 中查询是否存在该用户。查到的话，说明用户活跃，不仅将其转为 `UserDTO` 写入到当前请求的 `gin.Context` 中，还会重置/刷新该 Token 在 Redis 中的有效期（TTL）。**无论最终是否查到用户信息，这一层最后都会执行 `c.Next()` 进行放行。**
2. **第二层（鉴权中间件 `LoginInterceptor`）：**
   按需注册在需要保护的路由组上（比如下单、个人中心）。它的逻辑非常轻量，仅仅是去检查当前的 `gin.Context` 中有没有刚才第一层放进去的 User 信息。如果没有，说明未登录或 Token 失效，直接调用 `c.AbortWithStatusJSON` 拦截请求并返回 401 状态码；如果有，则执行 `c.Next()` 放行。

### **为什么必须设计成两层中间件？**

如果只用一层鉴权中间件并放在受保护的路由上，会导致一个**致命缺陷**：当用户一直在访问不需要登录的公开页面（如首页大厅、逛帖子）时，由于不经过拦截器，其在 Redis 中的 Token 存活时间得不到刷新，30 分钟后用户突然去下单，会发现自己莫名其妙掉线了。

因此采用两层中间件的设计不仅解决了上述问题，还有以下优势：

* **职责单一：** 全局中间件只专注一件事——"识别身份并刷新存活时间"；路由中间件只专注另一件事——"判断权限并决定是否拦截"。
* **兼顾性能与安全：** 特定页面强制拦截，公开页面允许匿名访问，但对于公开页面，如果侦测到携带了有效 Token，依旧可以默默为其刷新活跃状态，体验更平滑。
* **复用内存上下文：** 第一层中间件查到 Redis 数据后，通过 `c.Set` 将其保存在了当次请求的 `gin.Context`（请求级上下文）中。第二层中间件只需要 `c.Get` 读取内存即可，**避免了在同一次请求处理中对 Redis 的重复查询**，极大地节省了开销。


### 基于Cache Aside模式解决数据库与缓存的一致性问题

### **如何保证数据库与缓存的一致性的？**

我在项目中采用了经典的 **Cache Aside（旁路缓存）** 策略，主要满足绝大多数场景下的**最终一致性**需求：

* **读请求：** 先查询 Redis 缓存，如果命中则直接返回；如果未命中，则查询 MySQL 数据库，将结果写入 Redis 并设置合理的过期时间（TTL），最后返回数据。
* **写请求：** 先执行 MySQL 数据库的更新操作，更新成功后，**删除**对应的 Redis 缓存。这样下次有读请求过来时，就会触发缓存未命中，从而从数据库加载最新数据到缓存中。

### **为什么在写操作时，是"删除缓存"而不是"更新缓存"？**

主要有两个原因：

1. **避免无效的计算与写入：** 有些缓存数据并不是直接从数据库查出来的原样数据，而是经过多张表关联计算后得出的。如果每次修改数据库都去计算并更新缓存，而这个缓存可能很久才被访问一次，就会造成性能浪费（即延迟加载思想）。删除缓存的做法更为轻量。
2. **并发安全问题：** 在高并发场景下，如果是"更新缓存"，两个并发的写请求（线程 A 和 线程 B）可能会因为执行顺序的交错，导致数据库是 B 的最新值，但缓存却被回写成了 A 的旧值（脏数据）。直接删除缓存可以最大程度规避这种并发冲突。

### **为什么是"先更新数据库，再删除缓存"，而不是"先删除缓存，再更新数据库"？**

如果是**先删除缓存，再更新数据库**，在并发情况下极易产生脏数据：
线程 A 准备更新数据，先删除了缓存，还没来得及更新数据库；此时线程 B 来查询数据，发现缓存未命中，就会去查数据库，拿到了**旧值**，并把旧值写入缓存。等 A 更新完数据库后，缓存里依然是被 B 写入的旧数据，导致长时间的不一致。
而**先更新数据库，再删除缓存**的策略中，只有在"读请求恰好在缓存失效的瞬间并发，且写请求刚好发生在这个极短的间隙"这种极端情况下才会出现不一致，概率极低。配合缓存的 TTL 过期时间，可以作为兜底方案保证最终一致性。

### **如果交易数据要求更强一致性怎么办？**

Cache Aside 只能提供最终一致性，本项目不把它包装成强一致。交易场景应让数据库成为读写事实源，按业务选择版本号、事务锁、fencing token 或直接绕过缓存；单靠 Redis 分布式锁无法覆盖主从切换、租约过期和续期失败。


### 使用 Redis 缓解高频读取，并实现缓存穿透与击穿防护

### 什么是缓存穿透，怎么解决？

![image](https://github.com/user-attachments/assets/30fdea5c-f0ef-46f8-ab6f-cbfd65e78072)

**定义：**
大量并发请求去访问一个**数据库中根本不存在的数据**。由于缓存中没有该数据，导致请求全部打到数据库，而数据库也查不到数据，因此也无法写入缓存。这种现象叫缓存穿透。这会造成数据库瞬间压力过大、连接数等资源耗尽，最终导致数据库拒绝连接甚至宕机。
常见场景：1. 用户请求的 ID 在数据库中不存在；2. 恶意攻击者伪造大量不存在的 ID 发起请求。

**解决方法：**

1. **对请求增加校验机制**
   例如：在 HTTP 接入层或中间件拦截，如果字段 ID 是长整型，若请求携带的格式不符或为负数，则直接返回错误。
2. **使用布隆过滤器**

   ![image](https://github.com/user-attachments/assets/86652912-0713-426c-a842-0366067c4225)

   一句话总结布隆过滤器：一个名叫 Bloom 的人提出了一种来检索元素是否在给定大集合中的数据结构，这种数据结构是高效且性能很好的，但缺点是具有一定的错误识别率和删除难度。并且，理论情况下，添加到集合中的元素越多，误报的可能性就越大。布隆过滤器说某个元素存在，小概率会误判。布隆过滤器说某个元素不在，那么这个元素一定不在。

   为了避免穿透，可以在缓存前加一层布隆过滤器。系统启动时进行预热，将存在的商品/课程 ID 存入布隆过滤器；新增数据时同步写入。查询时，先判断 ID 是否在布隆过滤器中，如果不存在则直接拦截返回。
3. **缓存空值或特殊值（本项目应用方案）**

   ![image](https://github.com/user-attachments/assets/9d185eb4-4080-4bad-8d41-f4ba3a670372)

   请求通过了参数校验后，查询数据库发现数据不存在。此时我们**仍然将这个 Key 存入 Redis 缓存，但 Value 设置为空字符串（或特殊标识）**。
   *注意：为了防止占用过多内存或影响后续真实数据的写入，必须为这个空值缓存设置一个短暂的过期时间（TTL，如 2 分钟）。*

### 什么是缓存雪崩，怎么解决？

![image](https://github.com/user-attachments/assets/758bf96d-af23-4d89-91de-71f96c001be6)

**定义：** 缓存雪崩是指在同一时段，**缓存中大量的 Key 同时失效（或 Redis 服务宕机）**，导致大量高并发请求直接绕过缓存打到数据库，瞬间耗尽数据库资源，导致系统崩溃。
常见原因：对一大批业务数据（如首页推荐商品）设置了完全相同的缓存过期时间。

**解决方法：**

1. **对同一类型信息的 Key 设置不同的过期时间（常用）**
   在原有固定过期时间的基础上，加上一个随机的过期时间值，使它们的失效时刻被打散，避免同时过期。
   ```go
   // Golang 示例：设置过期时间为 300秒 + (0~100)秒的随机值
   expiration := time.Duration(300 + rand.Intn(100)) * time.Second
   rdb.Set(ctx, "course:"+courseId, data, expiration)
   ```
2. **使用互斥锁控制查询数据库的协程**
   当缓存失效时，通过锁机制（如 Go 的 sync.Mutex 或 Redis 分布式锁）控制，只允许一个 Goroutine 去查询数据库并重建缓存，其他 Goroutine 等待或重试。

3. **缓存预热与高可用**
   不用等到请求到来再去查询，提前由后台定时任务（Cron）将热点数据刷入缓存；同时搭建 Redis 哨兵或集群架构，防止 Redis 宕机引发的雪崩。

当前商铺缓存使用固定 TTL；随机 TTL 和高可用部署是后续治理选项，不作为本项目已落地能力。

### 什么是缓存击穿，怎么解决？
定义： 缓存击穿是指某一个被高并发访问的热点数据（Hot Key），在缓存失效的瞬间，海量请求同时去查询数据库，导致数据库瞬间被单点压力击垮。
常见场景：某爆款手机秒杀、微博热搜突发事件，当该热点数据的缓存刚好到期时。

解决方法：

- 基于互斥锁解决（本项目实现）

  - 思想：时间换空间。

  - 实现：使用 Redis 的 SETNX 指令（在 Go 中是 rdb.SetNX()）实现分布式互斥锁。缓存失效时，大量并发请求中只有一个 Goroutine 能成功获取锁去查 DB 并重建缓存，其余请求短暂等待后重新查询缓存。

  - 取舍：锁设置 TTL 防止永久占用，但等待会增加尾延迟；Cache Aside 仍是最终一致性，不应表述成强一致。


### 使用 Redis + Lua脚本实现对用户秒杀资格的预检，同时用乐观锁解决秒杀产生的超卖问题


### 为什么高并发秒杀要用 Redis + Lua？

在极高并发的秒杀场景下，我们需要同时进行**查询库存、判断库存是否充足、校验用户是否重复下单、扣减库存、记录订单**等多个操作。如果将这些操作拆分成多条 Redis 命令与 Go 代码交互，在并发协程（Goroutine）环境下会产生严重的竞态条件（Race Condition），导致数据不一致。

**核心优势：**
1. **原子性保障**：Redis 执行命令是单线程的，它会将整个 Lua 脚本作为一个整体放入队列中执行。在执行脚本期间，不会被其他客户端的命令打断，天然具备隔离性和原子性，**无需额外加分布式锁**。
2. **减少网络开销**：将多个 Redis 操作封装在一个 Lua 脚本中，只需要一次网络请求即可完成"资格预检"的全套逻辑，大幅降低了网络 RTT（往返时延），极大提升了秒杀接口的吞吐量。

---

### 说说秒杀下单的整体流程？

本项目采用 **"Redis 预扣减 + pending 记录 + MQ 异步落库"**，把数据库事务移出请求链路。完整流程如下：

1. **请求接收与 ID 生成**：Go 接入层接收请求，解析出用户 ID 和优惠券 ID，并通过 Redis 自研的全局唯一 ID 生成器（ID Worker）生成唯一的 `订单 ID`。
2. **Lua 脚本资格预检**：将 `优惠券 ID`、`用户 ID`、`订单 ID` 作为参数传入 Lua 脚本在 Redis 中执行。脚本内部会原子性地完成：
   - 判断库存是否大于 0。
   - 利用 Redis 的 `Set` 结构判断当前用户 ID 是否已存在（防止重复刷单）。
   - 若校验通过，则扣减 Redis 库存、记录用户资格，并原子保存 pending 订单。
3. **处理预检结果**：Go 代码根据 Lua 返回值（`0`: 成功, `1`: 库存不足, `2`: 重复下单）做出判断。若被拒绝则立即返回；通过后继续投递消息。
4. **投递与返回**：预检成功时 pending 已持久化；立即投递 **Kafka** 成功后清理 pending，失败则返回已受理的 `订单 ID`，由后台 relay 重投。
5. **后台异步落库**：后台的 Kafka Consumer 独立协程持续监听队列，拉取到订单消息后，再从容地去执行 MySQL 数据库的扣减真实库存和创建订单表记录逻辑。

### 什么是超卖问题，怎么解决？

![image](https://github.com/user-attachments/assets/6136ae13-f7b9-43cc-9a2e-83e23d4d1e49)

**定义：**
超卖问题是典型的高并发读写冲突问题。当优惠券仅剩最后 1 张时，由于并发执行，协程 A 查询库存发现剩余 1 张，在它还没来得及执行扣减操作时，协程 B 也来查询，同样发现剩余 1 张。最终两个协程都通过了校验并执行了扣减语句，导致库存变成负数，这就是超卖。

**常见的两种解决思路：**

* **悲观锁（Pessimistic Lock）：**
  * **思想**：添加强同步锁，让所有访问该资源的 Goroutine 排队串行执行。
  * **优点**：在锁服务和租约语义可靠的前提下，冲突模型直观。
  * **缺点**：性能极差，并发能力断崖式下降。
* **乐观锁（Optimistic Lock）：**
  * **思想**：不加锁，允许多个协程并行执行，只在最后更新数据库的那一刻去判断数据有没有被其他协程修改过。
  * **优点**：并发性能极佳，非常适合读多写少或短促高并发的场景。
  * **缺点**：如果设计不当，可能导致高并发下大量请求更新失败（成功率低）。

---

### 说一下乐观锁和悲观锁的底层概念？

* **悲观锁**：总是假设最坏的情况，认为共享资源每次被访问时都会被修改。因此每次在读取或操作数据前都会先上锁（如 MySQL 的 `FOR UPDATE` 行锁，或 Golang 中的 `sync.Mutex`）。其他试图获取该资源的协程将被挂起阻塞，直到持有者释放锁。
  * **适用场景**：多写场景，竞争极度激烈，且不允许重试的业务。
* **乐观锁**：总是假设最好的情况，认为并发冲突概率很低，无需加锁也无需阻塞等待。只在提交更新修改时，去验证数据是否在此期间被修改过。通常利用**版本号机制（Version）** 或 **CAS（Compare-And-Swap）算法**来实现（参考 Golang 的 `sync/atomic` 包中的原子操作）。
  * **适用场景**：多读少写，或期望系统维持高吞吐量的场景。

---

### 你在项目中具体使用的是哪种方式？

为了兼顾并发性能与数据库库存下限约束，MySQL 异步落库使用基于 **CAS 思想的条件更新**。

纯粹的 CAS（比较并交换）包含三个操作数：内存位置（V）、预期原值（E）和新值（N）。只有当 V == E 时，才将 V 更新为 N。但在秒杀场景下，如果严格使用版本号或精准比对库存（例如 `WHERE stock = 100`），100 个并发请求只有 1 个能成功，其余 99 个全部失败，导致成功率极低（明明还有 99 个库存）。

<img src="https://cdn.jsdelivr.net/gh/KNeegcyao/picdemo/img/image-20250307150305076.png" alt="image-20250307150305076" style="zoom: 33%;" />

因此，我结合业务特性做出了优化：

从业务的角度看，只要还有库存，就能执行扣减操作。所以我将 MySQL 的更新条件直接设计为 `WHERE stock > 0`。
利用 MySQL InnoDB 的**行级锁（Row Lock）**保证条件更新的原子性：有库存的请求可依次扣减，库存为零后更新失败，不会写成负数。

### 使用Redis分布式锁解决了在集群模式下一人一单的线程安全问题

### 为什么需要分布式锁？

在"秒杀"或"抢券"场景中，为了防止恶意用户利用并发漏洞批量刷券，我们的核心校验逻辑是：**根据"优惠券 ID"和"用户 ID"查询订单，如果不存在则创建。**

在单机部署下，可以用 Go 的 `sync.Mutex` 控制进程内并发；多实例之间不共享内存，因此本项目使用 Redis 锁协调同一用户与券的临界区。它不是“绝对互斥”：单 Redis 故障切换、租约过期和续期失败仍是边界，数据库唯一约束才是最终防线。

---

### Redis 分布式锁实现思路

为了理解分布式锁的底层语义，本项目没有依赖第三方锁库，而是使用 go-redis、唯一 token 和 Lua compare-and-delete 实现锁，并为 `RedissonLock` 增加有限等待与看门狗续期。

**1. 可重入性设计（规划中，当前未实现）**
同一个协程（Goroutine）在已经持有某把锁的情况下，可以再次获取该锁而不被阻塞。这有效避免了在复杂业务方法互相调用时发生死锁。
* **底层实现**：抛弃了简单的 `String` 结构，改用 Redis 的 `Hash` 数据结构来存储锁状态。
  * **大 Key**：锁的标识（如 `lock:order:1001:7`，由用户和券共同限定锁粒度）。
  * **小 Key (Field)**：当前获取锁的协程唯一标识（由 `UUID + GoroutineID` 拼接而成）。
  * **Value**：当前的重入次数（`count`）。每次重入时数值 +1；释放锁时数值 -1，只有当 `count` 减到 0 时，才真正删除该大 Key 释放锁。

<img src="https://cdn.jsdelivr.net/gh/KNeegcyao/picdemo/img/image-20241205233234744.png" alt="image-20241205233234744" style="zoom: 50%;" />

**2. 可重试与看门狗机制 (已实现)**
* **看门狗机制（自动续期）**：为了防止业务代码还没执行完，锁的有效期（TTL）就结束导致锁提前释放，我引入了类似 Redisson 的"看门狗"思想。加锁成功后，我会开启一个**独立的后台 Goroutine** 作为看门狗，它会每隔一段时间（如 TTL 的 1/3）利用 Lua 脚本去检查当前事务是否还持有锁。如果持有，就重新刷新锁的 TTL。业务执行完毕主动释放锁时，通过 Context 或 Channel 通知看门狗协程安全退出。
* **可重试**：在加锁方法中，我设计了等待时间与自旋逻辑。当协程 2 发现锁被协程 1 占用时，不会立即报错拒绝，而是在给定的等待时间内通过定时器不断尝试获取锁。由于高并发下大多数业务执行极快，协程 1 释放锁后，协程 2 能立马抢占到锁，这极大提升了系统的并发处理性能。

![](https://cdn.jsdelivr.net/gh/KNeegcyao/picdemo/img/image-20250307153056365.png)

**3. 解决主从一致性问题 (未实现)**
* **极端场景下的痛点**：在普通的 Redis 主从架构中，如果主节点刚写入锁就宕机了，且还没来得及同步给从节点，此时从节点被选举为新主节点，就会出现"锁丢失"。这就导致其他协程也能在新主节点上加锁成功，破坏了锁的互斥性。
* **可选升级**：多独立节点的 quorum lock 可以降低单点故障影响，但仍需评估时钟、网络分区和租约语义；对数据库写入还应配合 fencing token。当前项目没有实现这部分。

### 基于 Kafka 消息队列实现异步秒杀下单

### 为什么用异步秒杀（引入消息队列的背景）?

![image-20250307160040968](https://github.com/user-attachments/assets/30fdea5c-f0ef-46f8-ab6f-cbfd65e78072)

传统同步链路把资格校验、锁竞争和数据库事务都放在请求内，突发流量会直接放大数据库延迟。仓库当前的 `load` 标签直接调用 Service，不是 JMeter 或端到端容量证据。

**痛点分析：** 同步请求的整个业务流程是串行执行的：`查询优惠券 -> 校验资格 -> 查订单防重复 -> 减库存 -> 创建订单`。
这几步全都在直接操作 MySQL 数据库。MySQL 面对海量并发时的磁盘 I/O 瓶颈显而易见；再加上分布式锁的阻塞等待，导致大量 Goroutine 堆积，耗尽系统资源，最终系统崩溃。

### 怎么进行优化？（核心思想：削峰填谷与异步解耦）

![image-20241207220614455](https://cdn.jsdelivr.net/gh/KNeegcyao/picdemo/img/image-20241207220614455.png)


我们将极度耗时的同步阻塞逻辑，拆分为**"极速前置校验"**和**"后台异步落库"**两个阶段：

1. **极速前置校验（Redis + Lua）**：
   当用户发起下单请求时，直接在 Redis 中通过 Lua 脚本原子性地判断"库存是否充足"以及"该用户是否已下单"。如果条件满足，直接在 Redis 里扣减缓存库存，并将用户 ID 加入已购买集合。
2. **异步解耦（Kafka 消息队列）**：
   Redis 校验通过后原子保存 pending 订单，再尝试投递 **Kafka**。broker 确认后清理 pending；若投递失败，接口仍返回已受理订单 ID，后台 relay 继续重投。
3. **后台平滑落库（削峰填谷）**：
   后台 Goroutine 从 Kafka 拉取订单并按数据库可承受的速度落库。Kafka 可以吸收短时突发，但实际容量必须在独立环境做端到端压测后才能给出。

### 为什么选择 Kafka？

Kafka 适合可分区、可堆积且需要消费组扩展的事件流。这里选择它是为了将数据库写入从请求链路拆开；具体吞吐取决于 broker、分区、副本、消息大小和部署环境。

---

### 怎么降低 MQ 消息丢失风险？（可靠性问题）

这里不承诺不现实的“绝对不丢”：对已确认进入 Kafka 的消息，消费端实现可解释的 **At Least Once** 处理语义：

1. **Redis pending 记录**：V3 的 Lua 在扣库存和记录用户资格时，同一原子操作写入订单字段与 pending ID。即使请求 Context 随后取消，仍有完整 payload 可恢复。
2. **生产与重投**：`kafka.Writer` 使用 `Async=false`、`RequiredAcks=RequireAll`、单次尝试和写超时，把跨请求重试统一交给 pending relay，避免 Kafka 故障拖长请求与停机。立即投递成功后删除 pending；失败则返回已受理的订单 ID，由后台 relay 扫描并重投。删除失败只会产生重复消息。
3. **Broker 持久化**：Topic 应在部署时配置多副本和合理的 `min.insync.replicas`。这是环境约束，不是应用代码单方面能保证的能力。
4. **消费者手动提交**：使用 `FetchMessage` 拉取，订单事务成功后才调用 `CommitMessages`。处理失败时在当前消息上重试，不继续拉取并提交更高 offset；提交失败也原地重试。
5. **可等待退出**：HTTP 与消费者分别使用关闭期限；只有二者都退出后才关闭共享依赖。若硬超时，交给进程退出回收资源，避免在运行中的 Goroutine 下关闭 DB/Redis。

### 怎么防止消息被重复消费？（幂等性问题）

因为网络抖动或消费者宕机重试，不可避免地会出现同一条订单消息被拉取多次（At Least Once 语义）。我们需要保证消费逻辑的**幂等性**（即执行一次和执行一百次的结果是一样的）。

**本项目的解决方案：**
1. `tb_voucher_order` 同时有订单主键和 `(user_id, voucher_id)` 唯一索引，数据库是“一人一券”的最终防线。
2. 扣库存和插订单在同一个 MySQL 事务中；唯一键冲突会回滚库存扣减。
3. GORM 将唯一键冲突翻译为 `gorm.ErrDuplicatedKey`，业务再映射为 `ErrDuplicateOrder`。消费者把它视为“此前已处理成功”，随后提交 offset。

---

### 核心代码语义

```go
for {
    msg, err := reader.FetchMessage(ctx)
    if err != nil {
        // 读取失败重试或响应 shutdown
        continue
    }
    for process(msg) != nil {
        // 不拉下一条，避免后续 commit 跨过当前失败 offset
        waitRetry(ctx)
    }
    for reader.CommitMessages(ctx, msg) != nil {
        waitRetry(ctx)
    }
}
```

**当前边界：** Redis pending relay 解决了应用崩溃或 Kafka 短时失败后的可恢复投递，但仍依赖 Redis AOF/集群持久性，并允许幂等重复；它不是 Exactly Once。当前也没有 DLQ：格式错误消息会记录后提交，持续业务错误会阻塞消费，避免静默丢单。

### 社交功能：点赞、关注与共同关注

### 1. 为什么使用 ZSet 实现点赞？
对于高频变化的"点赞"数据，如果直接操作 MySQL 会引发严重的性能瓶颈。
我们需要一个能对点赞用户去重，且能 **"按点赞时间排序"**（用于展示点赞列表）的数据结构。
* **Redis ZSet (有序集合)** 同时提供 member 去重与 score 排序，适合点赞列表。
* **实现逻辑**：将点赞时间戳作为 `score`，用户 ID 作为 `member`。
  * **点赞/取消点赞**：当前实现先用 `ZScore()` 判断，再更新 DB 与 ZSet；高并发生产化需要 Lua 或数据库约束把状态切换做成原子操作。
  * **点赞列表展示**：利用 `ZRange` / `ZRevRange` 即可按时间顺序轻松查出前 N 名点赞用户。

### 2. 使用 Set 实现关注与共同关注
* **关注与取关**：使用 Redis 的 Set 集合存储某个用户的关注列表。关注即 `SADD follows:userID followUserID`，取关即 `SREM`。
* **共同关注**：利用 `SINTER follows:userA follows:userB` 在 Redis 内求交集，避免请求时执行 SQL 多表关联。

### 附近商铺搜索 (GEO)

在"附近商铺"功能中，由于需要计算两点之间的球面距离并进行半径范围筛选，传统数据库难以高效支撑。本项目采用 Redis 的 **GEO** 数据结构实现。

### GEO 核心原理与操作
* **底层实现**：GEO 的底层实际上是由 **ZSet** 实现的。Redis 通过 GeoHash 算法将二维的经纬度坐标映射为一维的整数值，作为 ZSet 的 `score` 进行存储和排序。
* **核心命令 (配合 go-redis)**：
  * **录入商户位置**：`GEOADD` (Go: `rdb.GeoAdd`)，将商户 ID 和经纬度存入缓存。
  * **附近搜索**：在早期的 Redis 中常用 `GEORADIUS`，但在较新版本中推荐使用功能更强大的 `GEOSEARCH` (Go: `rdb.GeoSearch`)。我们以用户的经纬度为中心，指定半径（如 5km），即可快速返回范围内的商铺 ID 列表及其距离，并支持按距离升序排列。

### 用户签到与连续签到统计 (BitMap)

### 为什么使用 BitMap？
签到本质上只有两个状态："已签到(1)"和"未签到(0)"。如果使用普通的数据库表或 Key-Value 存储，每个用户的每次签到都会产生一条记录，当用户基数庞大时，会消耗海量存储空间。
* **按位压缩**：一个用户一个月的签到值最多 31 bit；100 万用户的原始位数据约 3.7 MiB，但实际容量还要计入每个 Redis Key、对象和哈希表元数据。

### 核心实现思路
1. **签到**：以 `sign:userID:年月` 为 Key，将今天是本月的第几天作为 `offset` 偏移量。执行 `SETBIT key offset 1` (Go: `rdb.SetBit()`)。
2. **查询连续签到天数**：
   * 难点在于如何快速获知"从今天起往前连续签到了几天"。
   * 利用 `BITFIELD` 命令 (Go: `rdb.BitField()`) 一次性取出从本月第 1 天到今天的所有 bit 数据，它会返回一个十进制整数。
   * **位运算统计**：在 Go 代码中，通过循环对该整数进行 `按位与 1 (num & 1)` 的操作。若结果为 1，则连续签到天数 `+1`，随后将数字 `右移 1 位 (num >>= 1)` 继续判断，直到遇到 0 为止，极大提升了运算效率。

### UV 统计 (HyperLogLog)

### UV 与 PV 的痛点
* **PV (页面浏览量)**：可以直接用 Redis 的 `INCR` 计数。
* **UV (独立访客)**：需要去重。如果用 Set 或 BitMap 存储一天的所有独立用户 ID，当 UV 达到千万级别时，单 Key 的内存占用会非常恐怖（大 Key 问题）。

### HyperLogLog 解决方案
仓库提供带 `manual` 标签的 **HyperLogLog (HLL)** 误差验证，用于技术实验；目前没有接入 Handler/Service 业务链路。
* **核心优势**：基于概率估算算法，无论统计多少个不同的元素，单个 HLL 结构的内存占用**永远固定在最大 12KB 左右**！虽然有约 0.81% 的标准误差，但在宏观流量统计场景下完全可以忽略不计。
* **极简调用**：
  * **添加访客**：`PFADD key userID` (Go: `rdb.PFAdd()`)
  * **获取 UV 数**：`PFCOUNT key` (Go: `rdb.PFCount()`)
